# ヘッダーと RPC ごとの設定

## ヘッダー

ヘッダー名はクライアントの `ApiHeaders` と同じにする。サーバーは `Abstractions` に定数を置き、両方を一緒に直す。

| 向き | ヘッダー | 内容 |
| --- | --- | --- |
| リクエスト | `authorization` | `Bearer <token>`。`[SkipAuth]` の RPC には付かない |
| リクエスト | `x-request-id` | 冪等性の対象の RPC のみ(下の「RPC ごとの設定は属性に置く」)。1〜64 文字、英数字と `-` |
| リクエスト | `x-app-platform` | ios / android / windows / editor。今はログにだけ使い、強制アップデートを足したらその判定に使う |
| リクエスト | `x-app-version` | リリースごとに増やす整数。用途は `x-app-platform` と同じ |
| リクエスト | `x-game-date` | セッションの最初に受け取った日付(YYYY-MM-DD) |
| レスポンス | `x-server-time` | Unix 時間のミリ秒 |
| レスポンス | `x-game-date` | 今のゲーム内の日付 |

## RPC ごとの設定は属性に置く

Rust 版は proto の `idempotency_level` と `skip_auth` で RPC ごとの扱いを決めていた。C# では共有インターフェースの属性で持つ。

共有インターフェースは、`IService<T>` を継承し、サーバーとクライアントで共有するインターフェース。サービスのクラスは `ServiceBase<T>` の `T` にこれを渡す(MagicOnion はこの `T` をそのサービスとして登録する)。クライアントのラッパー(`ApiServiceBase<TService>`)の `TService` にも、同じインターフェースを渡す。

RPC は、共有インターフェースに直接書いたメソッドだけにする。共有インターフェースがほかのインターフェースを継承していても、そこから受け継いだメソッドには対応しない。MagicOnion はそのメソッドも RPC として登録するが、サーバーはその属性を読まず(属性が無いものとして、認証が要り、冪等性の対象になる)、クライアントのラッパーからは呼べない(`ArgumentException`)。

| 属性 | 意味 | 付けて効く場所 | 効く範囲 |
| --- | --- | --- | --- |
| `[SkipAuth]` | 認証の検証を省く(トークンを確かめない) | 共有インターフェース、またはそのメソッド | インターフェースに付けたらすべてのメソッド、メソッドに付けたらそのメソッド |
| `[NoSideEffects]` | 副作用がない。読み取り専用のトランザクションで動かす | 共有インターフェースのメソッド | そのメソッド |

冪等性の対象は、`[NoSideEffects]` も `[SkipAuth]` も付かない RPC。`[SkipAuth]` の RPC はプレイヤーが決まらないので対象にしない([冪等性](transaction.md#冪等性))。クライアントは冪等性の対象の RPC にだけ `x-request-id` を付け、1 つずつ順に送る(前の応答を受け取ってから次を送る)。

サーバーとクライアント(`RpcSettings`)は、共有インターフェースの属性だけを読む。実装クラスや実装クラスのメソッドに付けた属性は読まず、エラーにもならない(効くのは共有インターフェースに付けた属性だけ)。クライアントは実装クラスを知らないので、実装クラスの属性まで読むと、サーバーとクライアントで設定が食い違う。実装クラスがほかのインターフェースを実装していても、その属性は読まない。

- `[SkipAuth]` は `Interface | Method`、`[NoSideEffects]` は `Method` にだけ付けられる。それ以外(`[SkipAuth]` はクラス、`[NoSideEffects]` はクラスとインターフェース)に付けるとコンパイルエラーになる。実装クラスのメソッドにはどちらも付けられてしまうが、効かない

## 共通レスポンス項目

`player_diff`・バッジ・通知は、`IApiResponse` を実装した MessagePack の型で返す。
