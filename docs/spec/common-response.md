# 共通レスポンス項目

API のレスポンスに共通して載せる項目。サーバーは集めて詰め、クライアントは自動で反映する。VolTech-gRPC の共通レスポンス項目(`docs/wiki/api/common-response.md`)と同じ振る舞いにする。

| | player_diff | バッジ | 通知 |
| --- | --- | --- | --- |
| 何か | DB のデータの変更。クライアントのキャッシュをサーバーに合わせる | DB のデータから計算した、表示用の状態 | リクエスト中に起きた出来事(報酬を得た、ミッションをクリアした) |
| DB に保存するか | する(業務データそのもの) | しない(その場で計算する) | しない |
| クライアントでの扱い | Repository を更新する | バッジの状態を更新する | 待ち行列に積み、画面が都合のよいときに出す |

## 器

- 3 つの項目は、アプリが決める 1 つの型(以下 `TCommon`)にまとめる。基盤は `TCommon` の中身を知らない。player_diff・バッジ・通知のどれを持つか、どういう型で持つかはアプリが決める
- 共通レスポンス項目を返すレスポンスの型は、`Abstractions` の `IApiResponse<TCommon>` を実装し、`Common` に `TCommon` を持つ。RPC の戻り値は `UnaryResult<レスポンスの型>` のまま変えない
- `Common` が null なら、変化なし
- 1 つのアプリが使う `TCommon` は 1 つだけ。サーバーにもクライアントにも 1 つだけ登録する
- 共通レスポンス項目を使わないレスポンスは、`IApiResponse<TCommon>` を実装しない

## サーバー

- 共通レスポンス項目は、リクエストごとのコレクターに集める。コレクターはアプリが作り(`ICommonResponseCollector<TCommon>`)、サーバーに 1 つ登録する
- コレクターはトランザクションごとに 1 つ作る。業務の処理(書き込み関数など)が、トランザクションの書き込み口(`TxContext`)から取り出して記録する
- 本体が成功したら、基盤が同じトランザクションの中でコレクターから `TCommon` を作り、レスポンスの `Common` に入れる。冪等性の対象の RPC は、そのあとでレスポンスを保存する
- 失敗したら(ロールバック)、コレクターの中身も捨てる。エラーのレスポンスには共通レスポンス項目は付かない
- 同じ `x-request-id` の再送には、保存済みのレスポンスを `Common` ごと返す。通知が 2 回出ることはない(クライアントが 2 回反映しても、player_diff は変更後の値なので結果は変わらない)
- `[NoSideEffects]` の RPC と `[SkipAuth]` の RPC でも、レスポンスが `IApiResponse<TCommon>` なら詰める(例: ホームの取得でバッジを全種類返す)
- レスポンスが `IApiResponse<TCommon>` を実装しているのにコレクターが登録されていない、または登録したのと違う `TCommon` の `IApiResponse<>` を実装しているときは、基盤の設定の誤りとして `INTERNAL` にする
- `IApiResponse<>` のレスポンスを `RunAsync` の外で作ったとき、または `RunAsync` を通さなかったときは、`Common` が詰まらないので `INTERNAL` にする。本番でも動く。検出した時点で処理はコミット済みなので、主な目的は開発中に見つけること
- `RunAsync` は 1 回の RPC で 1 回だけ呼ぶ

## クライアント

- 成功したレスポンスが `IApiResponse<TCommon>` で、`Common` が null でなければ、呼び出し側に返す前に、アプリが登録した反映処理へ `Common` を渡す。反映処理は省略できる
- 反映は順番待ちの中で行う。次の API が送られる時点で、必ず反映が終わっている
- 古いセッションのレスポンス(通信中にタイトル・ホームに戻ったもの)は反映しない
- 反映処理で例外が起きたら、サーバーの処理は成功しているので再送はせず、`CLIENT_ERROR` として共通エラーハンドラーに渡し、呼び出し側には失敗を返す

## 項目ごとの決めごと

基盤は中身を知らないので、次はアプリが守る取り決めとして書く(VolTech-gRPC と同じ)。

- player_diff → バッジ → 通知の順で反映する
- player_diff の値は変化量ではなく変更後の値で持つ。同じ差分を 2 回反映しても結果が変わらない。無くなったものは、ID の一覧で別に持つ
- サインインなど全件を返すレスポンスは、差分ではなく、呼び出し側が `await` で受け取った後に置き換える
- バッジは、含まれない種類を「変化なし」とする。クライアントが同期しているデータから判定できるバッジはサーバーから返さない
- 通知は、運営からの「お知らせ」とは別物として呼び分ける。古いアプリは知らない種類を無視する
- 反映処理でやるのはデータの更新だけにし、ダイアログや画面遷移は書かない
