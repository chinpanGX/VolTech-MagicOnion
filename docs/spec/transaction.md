# 冪等性・トランザクション・ゲームログ

Rust 版の `transaction` クレートと同じ振る舞いを C# で再現する。

## トランザクション

- ハンドラーの本体を `ITransactions.RunAsync(Context, tx => ...)` で包む。成功でコミット、失敗でロールバックする
- `[NoSideEffects]` の RPC は読み取り専用のトランザクションにする。書き込むと DB がエラーを返すので、宣言の間違いに開発中に気づける
- `[SkipAuth]` の RPC はプレイヤーが決まらないので、`RunAsync` を使っても冪等性の対象にしない(普通のトランザクションで動かす)

## 冪等性

- 冪等性の対象の RPC(`[NoSideEffects]` も `[SkipAuth]` も付かないもの)は、同じ `x-request-id` の再送で本体を呼ばず、保存済みのレスポンスを返す
- 保存済みのレスポンスは、本体と同じトランザクションで書く。保存先の行が無ければ、基盤が同じトランザクションの中で作る。アプリがプレイヤー作成時に行を作る必要はない
- `x-request-id` が無い・形が違うときは `INVALID_ARGUMENT`
- `x-request-id` を別の RPC で使い回したら warn を出し、`INVALID_ARGUMENT` を返す
- 再送で保存済みのレスポンスを返したときは、ゲームログを書かない

## ゲームログ

プレイヤーのデータが「いつ・どの RPC で・どう変わったか」を残す。問い合わせを受けて、失ったアイテムや通貨を戻す(復帰処理)ときの根拠にする。アクセスログは RPC が呼ばれたことしか分からず、データがどう変わったかは追えないので、別に持つ。

- 出力先は DB の `game_logs`。本体と同じトランザクションで書く。ロールバックされた処理のログは残らず、コミットされた変更には必ずログがある。ログとデータが食い違わないので、復帰処理の根拠にできる
- `player_id`・`request_id`・RPC・時刻は基盤が付ける。アプリは何が変わったか(種類と内容)だけを渡す
- 再送で保存済みのレスポンスを返したときは書かない。同じ変更が二重に記録されないようにするため
